Working on the same code, together

How to set up your project so your whole team can build it — plus a Git cheatsheet two ways: in the terminal and in VS Code Source Control. Keep this open while you work.

01

How to structure your project

Your app has two halves — the frontend (React, what people see) and the backend (Express + MongoDB, the data). Both live in one repo, in two folders.

team-project/
├── .gitignore            # ignores node_modules + .env
├── README.md             # how to run the app
│
├── frontend/              # your React app (Vite)
│   ├── src/
│   │   ├── App.jsx
│   │   ├── main.jsx
│   │   └── components/
│   ├── index.html
│   └── package.json      # react, vite
│
└── backend/               # your Express API
    ├── server.js
    ├── models/            # Mongoose schemas
    ├── routes/            # GET / POST / PUT / DELETE
    ├── .env               # SECRET — never commit this!
    ├── .env.example       # blank template — safe to commit
    └── package.json      # express, mongoose, dotenv
  • One repo, one git clone. A teammate gets the whole app at once — the frontend and its matching backend never drift apart.
  • The two folders keep you from bumping into each other. One person works in frontend/, another in backend/ — you rarely touch the same file, so merge problems stay rare.
  • Two package.json files is normal. Run npm install inside both folders once, then start two servers in two terminals.
Security

Never commit your .env file. It holds your MongoDB password. Share it with teammates over chat instead, and commit a blank .env.example so everyone knows which keys they need.

02

Git cheatsheet

Every command, two ways. Pick whichever you like — both do exactly the same thing. Green = Terminal · Indigo = VS Code Source Control (the branch icon in the left bar, or Ctrl/Cmd Shift G).

status See what you've changed — before you commit
Terminal
$ git status
VS Code
  1. Open the Source Control panel (branch icon).
  2. Changed files appear under Changes. That list is your status.
commit Save a snapshot of your work, with a message
Terminal
# stage the files you changed $ git add . # save them with a message $ git commit -m "Add task form"
VS Code
  1. Hover a file, click + to stage it (or the + next to Changes for all).
  2. Type a message in the box at the top.
  3. Click the ✓ Commit button.
push Send your commits up to GitHub for teammates
Terminal
$ git push
VS Code
  1. Click Sync Changes (the ⟳ button after committing),
  2. or the ··· menu → Push.
pull Get your teammates' latest code onto your computer
Terminal
$ git pull
VS Code
  1. Click Sync Changes (it pulls and pushes),
  2. or the ··· menu → Pull.
stash Tuck unfinished work in a drawer, then get it back
Terminal
# hide changes so you can pull cleanly $ git stash # take them back out later $ git stash pop
VS Code
  1. Click the ··· menu → Stash → Stash.
  2. To bring it back: ··· → Stash → Pop Latest Stash.
When?

When do I stash? Git won't let you pull if you have unsaved changes it might overwrite. stash puts them safely aside so the pull works, then stash pop lays your work back on top.

04

Putting it online (hosting)

You host a full-stack app in three pieces, each in a different place. They connect over the internet, the same way they did on your computer. All three have free plans, and each one connects straight to your GitHub repo.

Piece 1 · Frontend

React app

→ Vercel

Import your GitHub repo, point it at the frontend/ folder, click deploy. Easiest win — start here.

Piece 2 · Backend

Express API

→ Render

New Web Service from your repo, root = backend/. Paste your secret keys into its Environment tab.

Piece 3 · Database

MongoDB

→ Atlas

Already done! You're using Atlas in class, so your database is already in the cloud. Nothing to move.

Watch out

The one thing that always breaks: the API address. In class your React app calls http://localhost:5000. Once hosted, the backend lives at a new address like https://your-app.onrender.com. Save that address in one variable (e.g. API_URL) so you only change it in one place — not in every fetch().

Take it slow

One piece at a time. Hosting is a real level-up. Get the frontend live first (it's the simplest and most exciting to share), then do the backend, then connect the two. You don't have to do it all in one day.

05

Deploy straight from your GitHub repo

Both hosts read your code from GitHub and rebuild every time you git push. Because your frontend and backend share one repo, the only real trick is telling each host which folder to build — the Root Directory setting.

Root Directory The one setting that makes a shared repo work
Vercel · frontend
Root Directory
frontend
Framework
Vite
Build Command
npm run build
Output Directory
dist
Environment
VITE_API_URL = your Render URL
Render · backend
Root Directory
backend
Runtime
Node
Build Command
npm install
Start Command
node server.js
Environment
MONGO_URI = your Atlas string

Do it in this order:

  1. Push your repo to GitHub. Both hosts connect to it from there.
  2. Backend first, on Render. New Web Service → pick your repo → set Root Directory to backend → add MONGO_URI → deploy. Copy the URL it hands you, like https://your-app.onrender.com.
  3. Frontend on Vercel. Import the same repo → set Root Directory to frontend → add VITE_API_URL = the Render URL → deploy.
  4. Every push redeploys. After this, git push updates the live site on its own — no extra steps.
CORS

Let the frontend talk to the backend. By default the browser blocks your Vercel site from calling your Render API, because they live at different addresses. In server.js, install and enable cors — app.use(cors()) allows everyone, or pass your Vercel URL to allow only your site.

Secrets

Env vars live on the host, not in the repo. Your .env is gitignored, so retype those keys in each host's Environment settings. That's why MONGO_URI goes in Render and VITE_API_URL goes in Vercel — the repo never carries them.
